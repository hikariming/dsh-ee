# अनुमतियाँ और एक्सेस नियम: त्वरित संदर्भ

## तीन स्तर

dsh-ee का एक्सेस नियंत्रण तीन स्तरों में बँटा है, बदलाव के प्रवेश प्रशासन बैकएंड में हैं, और कॉन्फ़िगर करते ही तुरंत प्रभावी होते हैं।

| स्तर | किस प्रश्न का उत्तर | कॉन्फ़िगरेशन प्रवेश | कॉन्फ़िगर करने के बाद कौन प्रभावित |
| --- | --- | --- | --- |
| अनुमति कोड | यह व्यक्ति यह सुविधा उपयोग कर सकता है या नहीं | “भूमिकाएँ और अनुमतियाँ” | पेज दिखना/छिपना, API कॉल |
| फ़ील्ड और एक्सेस नियम | यह फ़ील्ड, यह डेटा देखा या बदला जा सकता है या नहीं | “फ़ील्ड और एक्सेस नियम” | दस्तावेज़, ज्ञान आधार, उपयोगकर्ता आदि एक्सटेंशन फ़ील्ड |
| प्रशासनिक प्रतिबंध | महत्वपूर्ण कॉन्फ़िगरेशन बदलने पर स्वीकृति चाहिए या नहीं | “फ़ील्ड और एक्सेस नियम” | फ़ील्ड मान बदलने, कॉन्फ़िगरेशन बदलने के ऑपरेशन |

## अनुमति कोड पेज और API पर कैसे लागू होते हैं

मेन्यू केवल “दिखेगा या नहीं” तय करता है, असली सीमा API में है। पेज पर बटन छिपाना सुरक्षा सीमा नहीं बनता।

| सामान्य अनुमति कोड | भूमिका | कर्मचारी के पास डिफ़ॉल्ट रूप से है या नहीं |
| --- | --- | --- |
| `portal.view` | वर्कबेंच, कंपनी ऐप, विकास दस्तावेज़ आदि कर्मचारी पेजों का उपयोग | है |
| `registry.publish` | प्लगइन, स्किल, प्रॉम्प्ट और ऐप प्रकाशित करना | है |
| `extensions.develop` | एक्सटेंशन विकास स्किल और कमांड निर्देश प्राप्त करना | नहीं, व्यवस्थापक को देना होगा |
| `plugins.manage` | समीक्षा तथा सूचीबद्ध करने/हटाने की क्षमता | नहीं |
| `connections.manage` | कंपनी कनेक्शन जोड़ना और कॉन्फ़िगर करना | नहीं |

अनुमति कोड कोड में अंतर्निहित निर्देशिका से डेटाबेस में सिंक होते हैं; नए संस्करण में जोड़े गए अनुमति कोड “कर्मचारी” भूमिका को स्वतः दिए जाते हैं (यदि निर्देशिका में डिफ़ॉल्ट भूमिका अंकित हो)।

## एक्सेस नियमों का मूल्यांकन क्रम

1. सुपर व्यवस्थापक: नियमों से सीमित नहीं (जब तक सिस्टम में सुपर व्यवस्थापक बंद न हो)।
2. भूमिका अनुमतियाँ: पहले तय करें कि यह सुविधा स्वयं दिखती है या नहीं।
3. फ़ील्ड एक्सेस नियम: फ़ील्ड-दर-फ़ील्ड read / write / deny तय करें, नियम में शर्तें हो सकती हैं।
4. प्रशासनिक प्रतिबंध: राइट ऑपरेशन के लिए पहले परिवर्तन सबमिट करना है या नहीं, और कौन स्वीकृति देगा।

पहले के स्तर निष्कर्ष दे दें तो बाद के स्तर उसे ढीला नहीं करते।

## कॉन्फ़िगरेशन प्रवेश और उदाहरण

| मैं चाहता/चाहती हूँ | कहाँ जाएँ |
| --- | --- |
| किसी प्रकार के कर्मचारियों को एक्सटेंशन विकास सामग्री खोलना | “भूमिकाएँ और अनुमतियाँ” → `extensions.develop` दें |
| कोई फ़ील्ड केवल अपने विभाग को दिखे | “फ़ील्ड और एक्सेस नियम” → नया read नियम बनाएँ, शर्त में विभाग चुनें |
| दस्तावेज़ का “गोपनीय” फ़ील्ड निर्यात न हो | वही करें, एक deny नियम जोड़ें और API प्रतिक्रिया जाँचें |
| महत्वपूर्ण फ़ील्ड बदलने से पहले स्वीकृति | “फ़ील्ड और एक्सेस नियम” → प्रशासनिक प्रतिबंध → परिवर्तन अनुरोध बाँधें |

## एक्सटेंशन लिखते समय कैसे सहयोग करें

- मैनिफ़ेस्ट में आवश्यक अनुमति कोड और क्रेडेंशियल नाम घोषित करें, क्रेडेंशियल कोड या मैनिफ़ेस्ट में न लिखें।
- फ़ील्ड के पढ़ने/लिखने के नियम व्यवस्थापक कॉन्फ़िगर करता है; एक्सटेंशन केवल API की लौटाई दिखने वाली फ़ील्ड संभाले, स्वयं अनुमतियों का अनुमान न लगाए।
- एरर कोड में “अनुमति नहीं”, “मौजूद नहीं” और “पैरामीटर गलत” अलग रखें, इन सभी को 500 में न लौटाएँ।
