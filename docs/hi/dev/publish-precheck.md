# प्रकाशन प्रवेश और प्रीचेक परिणाम कैसे पढ़ें

## तीन प्रकाशन प्रवेश

| प्रवेश | पथ | उपयुक्त परिदृश्य | प्रीचेक कब चलता है |
| --- | --- | --- | --- |
| वेब अपलोड | वर्कबेंच “प्लगइन साझा करें” | पहली बार प्रकाशन, प्रीचेक देखते हुए सुधारना चाहते हों | अपलोड के तुरंत बाद |
| npm सीधा प्रकाशन | `npm publish --registry <कंपनी रजिस्ट्री>` | पहले से CI हो, संस्करण पाइपलाइन के अनुसार प्रकाशन | प्रकाशन के समय |
| Agent API | `POST /api/agent/packages` | स्वचालित प्रकाशन और बैच माइग्रेशन | प्रकाशन के समय |

तीनों प्रवेश एक ही प्रवेश नियमों से गुज़रते हैं: पैकेज पहले स्टैटिक प्रीचेक से, फिर प्रकाशन टकराव की जाँच से, अंत में कलेक्शन मोड के अनुसार या तो सीधे सूचीबद्ध होता है या समीक्षा में जाता है।

## प्रीचेक क्या स्कैन करता है

प्रीचेक केवल पैकेज खोलकर स्टैटिक जाँच करता है, **प्लगइन कोड निष्पादित नहीं करता**, डेटाबेस में नहीं लिखता और संस्करण संख्या भी अधिकृत नहीं करता। परिणाम pass / warn / fail तीन स्तरों में होते हैं।

| स्कैन कुंजी | किस पर ध्यान देती है | गंभीरता |
| --- | --- | --- |
| `bundle` | `dsh.bundle` और patch फ़ाइलें: अनुपस्थित, असुरक्षित पथ, फ़ाइल पैकेज में नहीं | प्लगइन पैकेज के लिए fail; गैर-प्लगइन पैकेज में अनुपस्थित होना चेतावनी |
| `patch` | `cordis.patch.yml` की संरचना (सरणी, `insert`, `id`/`name`, दोहराया id) | संरचना त्रुटि fail; नाम बेमेल आदि चेतावनी |
| `cordis` | `dependencies` में Cordis संबंधित पैकेज मिले या नहीं | चेतावनी |
| `cordis-peer` | `peerDependencies` की Cordis सीमा अनुशंसित मान से भटकी है या नहीं | चेतावनी |
| `skills` | पैकेज के साथ वितरित स्किल सूची | चेतावनी (समीक्षा में यह दिखेगा) |
| `install-scripts` | इंस्टॉल के समय चलने वाली स्क्रिप्ट (`preinstall` आदि) | चेतावनी |
| `secrets` | पैकेज में संदिग्ध कुंजी मिलती है या नहीं | **fail** |
| `license` | SPDX लाइसेंस घोषित है या नहीं | **चेतावनी** (रोकता नहीं) |
| `engines` | प्लगइन `engines.dsh` घोषित करता है या नहीं | चेतावनी |
| `dependencies` | गैर-कंपनी scope वाली निर्भरताओं की सूची | जानकारी |
| `size` | पैकेज का आकार (20 MB से अधिक पर चेतावनी) | चेतावनी |

प्रीचेक केवल यह बताता है कि “कंपनी इस पैकेज को सुरक्षित रूप से स्वीकार कर सकती है या नहीं”; गुणवत्ता का मूल्यांकन नहीं करता, न प्लगइन को श्रेणी या क्रम देता है। मानक और चेकर अपस्ट्रीम टूलचेन के हैं, उनके निष्कर्ष लेखक की स्व-प्रमाण सामग्री हैं और कंपनी प्रीचेक में नहीं मिलाए जाते।

## परिणाम कैसे पढ़ें

प्रीचेक तीन निष्कर्ष फ़ील्ड लौटाता है, जो प्रकाशन API के वास्तविक व्यवहार से मेल खाते हैं:

| निष्कर्ष फ़ील्ड | अर्थ |
| --- | --- |
| `can_submit` | प्रकाशन टकराव नहीं है, प्रकाशन API यह पैकेज स्वीकार करेगा |
| `will_publish` | ओपन कलेक्शन मोड में जाँच में कोई fail मद नहीं, प्रकाशित होते ही सूचीबद्ध |
| `requires_review` | सबमिट किया जा सकता है, पर समीक्षा कतार में जाएगा |

वास्तव में “सीधे सूचीबद्ध या समीक्षा में” कलेक्शन मोड और fail मदें तय करती हैं:

| स्थिति | व्हाइटलिस्ट मोड (डिफ़ॉल्ट) | ओपन मोड |
| --- | --- | --- |
| प्रकाशन टकराव (पैकेज नाम / संस्करण अधिकृत / scope / स्वामित्व / समान नाम वाला अपस्ट्रीम पैकेज) | प्रकाशन API अस्वीकार कर देता है | वही |
| fail मदें (जैसे secrets, bundle संरचना त्रुटि) | सबमिट हो सकता है, समीक्षा में जाएगा; **अस्वीकृति नहीं** | सबमिट हो सकता है, समीक्षा में जाएगा |
| केवल चेतावनी मदें, या सभी pass | समीक्षा में जाएगा | कोई fail मद नहीं, प्रकाशित होते ही सूचीबद्ध |

सबमिट सफल होते ही संस्करण संख्या अधिकृत हो जाती है; अस्वीकृत या हटाए गए संस्करण भी दोबारा प्रकाशित नहीं हो सकते, ठीक करने के बाद संस्करण संख्या बढ़ाएँ।

## सबमिट से पहले स्व-जाँच

1. `pnpm build` के बाद पैकेज बनाएँ, पुष्टि करें कि `files` व्हाइटलिस्ट में सभी आउटपुट शामिल हैं।
2. `dsh-primer check` और `npx dsh-standards@1.6.9 check .` स्थानीय रूप से एक बार चलाएँ और परिणाम लेखक रेपो CI में रखें।
3. पैकेज में `.tgz`, सोर्स मैप, टेस्ट फ़िक्स्चर की वास्तविक कुंजियाँ और स्थानीय निरपेक्ष पथ न हों।
4. `license`, `engines.dsh` और DSH संस्करण लाइन स्पष्ट लिखें, ताकि बेमेल इंस्टॉल के समय ही सामने न आए।
5. इंस्टॉल के समय चलने वाली स्क्रिप्ट चाहिए तो सबमिट विवरण में स्पष्ट लिखें कि स्क्रिप्ट क्या करती है।

## सामान्य प्रश्न

| लक्षण | सामान्य कारण | समाधान |
| --- | --- | --- |
| प्रीचेक प्रकाशन टकराव दिखाता है | पैकेज नाम कंपनी scope में नहीं, संस्करण पहले से मौजूद, समान नाम वाला अपस्ट्रीम पैकेज | ये टकराव प्रकाशन API सीधे अस्वीकार कर देते हैं; पहले पैकेज नाम बदलें या संस्करण बढ़ाएँ |
| प्रीचेक में fail मद है | bundle/patch संरचना त्रुटि, या संदिग्ध कुंजी मिली | पहले ठीक करें फिर सबमिट करें; fail मद के साथ भी सबमिट हो सकता है, पर समीक्षा में जाएगा और संस्करण अधिकृत हो जाएगा |
| सबमिट के बाद समीक्षा में | व्हाइटलिस्ट मोड, या ओपन मोड में fail / चेतावनी मदें | समीक्षा टिप्पणी के अनुसार सुधारें; एक ही समस्या को नए संस्करण से बार-बार आज़माएँ नहीं |
| समीक्षा में देर तक निष्कर्ष नहीं आता | इंस्टॉल स्क्रिप्ट, निर्भरताएँ या संवेदनशील सामग्री के लिए मैनुअल पुष्टि आवश्यक | विवरण में जानकारी जोड़ें, या व्यवस्थापक से संपर्क करें |
| कंपनी में इंस्टॉल के बाद संस्करण गलत | क्लाइंट कैश, या पुराना संस्करण निर्दिष्ट | `dsh plugin add <पैकेज>@<संस्करण>` में संस्करण की पुष्टि करें |
