# DSH प्लगइन लिखें और कंपनी रजिस्ट्री में प्रकाशित करें

## पूर्वापेक्षाएँ

| निर्भरता | संस्करण | क्यों आवश्यक |
| --- | --- | --- |
| Node | ≥ 24.9.0 | `dsh-primer` और `dsh-standards` के `engines` दोनों ≥24.9 माँगते हैं; DSH 0.2.2 लाइन भी Node ≥24.9 माँगती है, पुरानी 0.2.x लाइन 22.19+ पर चल सकती है |
| DSH | 0.2.x लाइन (0.2.1–0.2.2) | प्लगइन चलाने और `dsh plugin add` के लिए; `dsh-primer` `>=0.2.1-0 <0.3.0` समर्थन घोषित करता है, `engines.dsh` वास्तव में सत्यापित सीमा के अनुसार भरें |
| pnpm | कोई भी हाल का संस्करण | निर्भरताएँ इंस्टॉल करना और पैकेजिंग |
| dsh-primer | 0.4.x | स्कैफ़ोल्ड, स्टैटिक जाँच और इंस्टॉल स्मोक (पुराना नाम `dsh-plugin-guide` 0.3.x, CLI पुराना उपनाम `dsh-plugin-dev`) |
| कंपनी खाता | “प्रकाशन क्षमता” (`registry.publish`) हो | प्लगइन अपलोड करना, समुदाय प्लगइन लाने का अनुरोध करना |

## पाँच मिनट में एक स्कैफ़ोल्ड

```bash
# 0. dsh-primer 是可安装的 DSH bundle，不是 DSH 自带命令；先装进你用的 profile
dsh plugin --profile web add dsh-primer

# 1. 生成骨架（上游模板，TypeScript）
dsh-primer new my-plugin

# 2. 本地装依赖并跑通
cd my-plugin
pnpm install
pnpm build

# 3. 自查包形状（静态检查，在本地执行）
dsh-primer check

# 4. 装进一个测试 profile 验证加载/卸载
dsh-primer verify
```

`dsh-primer` अपस्ट्रीम टूलचेन का हिस्सा है; dsh-ee केवल संस्करण निश्चित करता है और उपयोग बताता है, इसकी जाँच लॉजिक दोहराता नहीं।

## मैनिफ़ेस्ट में कंपनी के लिए सबसे महत्वपूर्ण फ़ील्ड

| फ़ील्ड | क्या लिखें | कंपनी पक्ष क्यों देखता है |
| --- | --- | --- |
| `name` | कंपनी scope के अंतर्गत पैकेज नाम, जैसे `@company/hello` | तय करता है कि कंपनी npm रजिस्ट्री तक रूटिंग हो सकेगी या नहीं |
| `version` | सेमांटिक संस्करण, एक बार में एक संस्करण | संस्करण संख्या एक बार ले ली जाए तो वापस नहीं जाती; प्रकाशन टकराव सबमिट अस्वीकार कर देता है |
| `main` / `files` | वास्तव में प्रकाशित होने वाला प्रवेश और फ़ाइल व्हाइटलिस्ट | स्रोत कोड, टेस्ट और `.tgz` साथ न भेजे जाएँ |
| `cordis.patch.yml` | Cordis के लिए प्लगइन के पैच की घोषणा | प्रीचेक bundle और patch की संरचना जाँचता है |
| `dsh.bundle` | DSH प्लगइन मैनिफ़ेस्ट (यदि हो) | तय करता है कि क्लाइंट इस पैकेज को पहचान सकेगा या नहीं |
| `engines.dsh` | वास्तव में सत्यापित DSH संस्करण सीमा | कंपनी की DSH संस्करण लाइन से मिलाएँ; न घोषित करने पर चेतावनी मिलेगी |
| `peerDependencies` | DSH संबंधित peer | प्रीचेक जाँचता है कि peer सीमा हल हो सकती है या नहीं |
| `license` | `Apache-2.0` जैसे SPDX पहचानकर्ता | license न होना प्रीचेक की **चेतावनी** मद है (रोकता नहीं), पर मैनुअल समीक्षा में जाएगा |

## स्थानीय स्व-जाँच क्या-क्या जाँचती है

| कमांड | क्या जाँचता है | कहाँ चलाएँ |
| --- | --- | --- |
| `dsh-primer check` | पैकेज का आकार और प्रवेश पूर्ण हैं या नहीं | लेखक की मशीन या लेखक रेपो CI |
| `dsh-primer verify` | इंस्टॉल, सक्षम और अनइंस्टॉल का स्मोक | लेखक की मशीन या लेखक रेपो CI |
| `npx dsh-standards@1.6.9 check .` | अपस्ट्रीम मानक धाराओं का स्टैटिक प्रमाण (Node ≥24.9 चाहिए) | लेखक की मशीन या लेखक रेपो CI, निष्कर्ष लेखक की स्व-प्रमाण सामग्री है |

dsh-ee का सर्वर प्लगइन कोड निष्पादित नहीं करता और इन चेकरों को भी नहीं चलाता; वेब पेज का “प्लगइन साझा करें” प्रीचेक केवल पैकेज के स्टैटिक आकार और कंपनी प्रवेश शर्तें देखता है।

## कंपनी रजिस्ट्री में प्रकाशित करें

| प्रवेश | कैसे करें | किसके लिए उपयुक्त |
| --- | --- | --- |
| वर्कबेंच “प्लगइन साझा करें” | `.tgz` अपलोड करें, पहले प्रीचेक परिणाम देखकर सबमिट करें | पहली बार प्रकाशन, प्रीचेक पहले देखना चाहते हों |
| npm सीधा प्रकाशन | `npm publish --registry <कंपनी रजिस्ट्री>`, टोकन “मेरे टोकन” में बनाएँ | पहले से CI पाइपलाइन हो |
| Agent API | `POST /api/agent/packages`, कंपनी टोकन से कॉल करें | स्वचालित प्रकाशन |

समीक्षा और सूचीबद्धता के दौरान संस्करण संख्या अधिकृत रहती है; दोहराया संस्करण या टकराव अस्वीकार होगा। प्रीचेक निष्कर्ष तीन हैं: `can_submit` (प्रकाशन टकराव नहीं, प्रकाशन API पैकेज स्वीकार करेगा), `will_publish` (ओपन कलेक्शन मोड में जाँच में कोई fail मद नहीं, प्रकाशित होते ही सूचीबद्ध), `requires_review` (सबमिट के बाद समीक्षा में जाएगा)।

## सामान्य प्रश्न

| लक्षण | सामान्य कारण | समाधान |
| --- | --- | --- |
| प्रीचेक प्रवेश फ़ाइल न होने की चेतावनी देता है | `files` व्हाइटलिस्ट में बिल्ड आउटपुट नहीं, या `main` किसी अनबिल्ट फ़ाइल की ओर इशारा करता है | पहले `pnpm build`, फिर `files` जाँचें |
| प्रीचेक में fail मद है | bundle / patch संरचना त्रुटि, संदिग्ध कुंजी मिली आदि | पहले ठीक करें फिर सबमिट करें; fail मद के साथ भी सबमिट हो सकता है, पर संस्करण अधिकृत हो जाएगा और समीक्षा भी सामान्यतः पास नहीं होगी |
| प्रीचेक में केवल चेतावनी मद है | license नहीं, `engines.dsh` घोषित नहीं, इंस्टॉल स्क्रिप्ट आदि | रोकता नहीं: व्हाइटलिस्ट मोड में मैनुअल समीक्षा, ओपन मोड में सीधे सूचीबद्ध |
| peer सीमा हल नहीं होती | दो असंगत DSH संस्करण लाइनें साथ घोषित | केवल एक संस्करण लाइन रखें, या हल होने वाली सीमा पूरी करें |
| इंस्टॉल पर Node संस्करण की त्रुटि | `engines.node` और कर्मचारी के कंप्यूटर का Node मेल नहीं खाता | वास्तविक सत्यापन के अनुसार `engines.node` सुधारें (उदाहरण: `^22.19.0 \|\| >=24.9.0`) |
| कंपनी में इंस्टॉल नहीं होता | टोकन अनुमति अपर्याप्त या npmrc में कंपनी रजिस्ट्री कॉन्फ़िगर नहीं | “इंस्टॉल क्षमता” अनुमति और `.npmrc` जाँचें |
