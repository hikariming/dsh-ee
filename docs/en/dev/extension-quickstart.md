# Write a dsh-ee extension: manifest, checks and calls

## Four forms

dsh-ee extensions bring company systems in. Choose the form first: the first three are delivered as a manifest, and the fourth is an official integration implemented by dsh-ee itself, for which authors do not write a manifest.

| Form | Manifest `kind` | Where it runs | Deliverable | How dsh-ee calls it |
| --- | --- | --- | --- | --- |
| Declarative | `declarative` | HTTP requests sent from inside the dsh-ee process | Manifest + OpenAPI document (zip) | Generates tools from the OpenAPI document and calls the source system directly |
| Service | `service` | An HTTP service the company deploys itself | A service that implements the manifest and the agreed interface | Fetches `/.well-known/dsh-ee-extension.json`; tools go through `POST /mcp` |
| Local | `local` | An npm package on employee machines | npm package + manifest | The Agent connects to the local MCP directly; write operations ask dsh-ee for confirmation first, and a summary is reported after the call |
| Built-in | (no manifest) | Go inside the dsh-ee process | Ships with dsh-ee upgrades | Same internal interface as service extensions, no network (e.g. a Feishu document knowledge source) |

The manifest schema only accepts the three `kind` values `declarative` / `service` / `local`; "built-in" is implemented by dsh-ee itself and cannot be delivered through a manifest. The server does not run third-party code: for declarative extensions dsh-ee sends the requests, service extensions run in the company's own service, and local extensions run on employee machines.

## Scaffold an extension

```bash
# 声明式：不写代码，有 OpenAPI 就能接
dsh-ee extension init ./my-ext --id acme/my-ext --kind declarative

# 服务式：要写逻辑，企业自己部署
dsh-ee extension init ./my-service --id acme/my-service --kind service
```

`init` must specify the identity with `--id <author>/<name>`; `--kind` accepts `declarative` (default) or `service`. Copy local extensions from the [`extensions/official/legacy-local`](https://github.com/hikariming/dsh-ee/blob/main/extensions/official/legacy-local) template or example in the repository. The generated directory contains an `AGENTS.md`; open it with an Agent and it knows the next step.

| Command | Purpose | What it does locally |
| --- | --- | --- |
| `dsh-ee extension init` | Copies an extension from the example | Writes files |
| `dsh-ee schema list` / `schema get manifest` | Look up specifications such as the manifest and error codes offline | Read-only |
| `dsh-ee extension check` | Statically checks the manifest, API document, read-only flags and credential usage | Read-only checks, no code execution |
| `dsh-ee extension test` | Starts the service extension and tests it item by item against the protocol | Starts a local process |
| `dsh-ee extension dev` | Starts a mock dsh-ee (no database needed) | Starts a local process |
| `dsh-ee extension call` | Calls an extension tool once as a given employee | Read-only diagnostics |
| `dsh-ee extension pack` | Packs a **declarative** extension into a zip and computes its checksum | Writes a zip |
| `dsh-ee extension report` | Generates a delivery note for administrators | Writes files |

`check` exits with code 1 when there are errors, and every result carries `code`, `severity`, `where`, `message` and `fix`. All the commands above run on the author's machine or in the author's repo CI; the dsh-ee server does not execute third-party code, and does not run checkers in the web page either.

## Minimal manifest example

The manifest below matches the shape generated by `dsh-ee extension init --kind declarative`; after pairing it with an `openapi.yaml` covered by `servers`, `dsh-ee extension check` reports 0 errors and 0 warnings. Fields follow `dsh-ee schema get manifest`; the manifest is a strict schema, and an extra field not in the specification is an error too.

```json
{
  "id": "acme/oa",
  "version": "0.1.0",
  "name": "Acme OA",
  "description": "查询和提交 Acme OA 的审批单。",
  "kind": "declarative",
  "openapi": "openapi.yaml",
  "servers": ["https://oa.acme.internal"],
  "credential": { "mode": "ee_jwt" },
  "tools": [
    {
      "name": "list_items",
      "readOnly": true,
      "description": "列出当前员工的条目",
      "keep": ["items.id", "items.title", "total"]
    },
    {
      "name": "create_item",
      "description": "新建一个条目。这是写操作，调用前要员工确认。"
    }
  ]
}
```

A few easy mistakes:

- `id` must be written as "author/name" using only lowercase letters, digits and hyphens; `version` is a strict semantic version.
- A declarative extension must have `openapi` (a relative path inside the extension directory) and at least one `servers` entry; `servers[0].url` in the OpenAPI document must fall within the manifest's `servers`.
- `tools[].name` corresponds to each OpenAPI operation's `operationId`; mark query tools as `readOnly`, and do not mark write operations.
- The credential mode (`credential.mode`) is only needed at call time: `shared` / `user_secret` / `ee_jwt` / `oauth`; choose the one the other side accepts.

## Confirm before delivery

| Check item | Where to confirm |
| --- | --- |
| Manifest fields and protocol version | `dsh-ee schema get manifest`, `dsh-ee extension check --json` |
| API document and tool mapping | The `tools` results from `check`; whether write operations are marked `readOnly` |
| Credentials only come from dsh-ee, never written into the manifest | No plaintext key appears in the manifest or the code |
| Protocol consistency of the service interface | Test cases from `dsh-ee extension test` |
| Declarative packaging | `dsh-ee extension pack` produces a zip; service extensions deliver a code repository or image |
| Who can use which tools | Administrators configure it in "Connections" and "Fields & access rules" |

## Relationship to DSH skills

To give the Agent an executable instruction, dsh-ee wrote the extension development flow as a skill (`dsh-ee-extension-dev`) and distributes it to DSH under the "Develop extensions" (`extensions.develop`) permission. People and Agents see the same steps: the page is for humans to read, and the skill is for the Agent to execute.
