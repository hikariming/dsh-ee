# 可扩展的权限：管理角色与扩展字段（草案，2026-11-11）

> 状态：第 3、4 批已经做出来（进度见 [plugins.md](./plugins.md) §12.2）；§8 的两个问题按建议做了：字段先覆盖文档、知识库、用户，不做按人单独授权。和 [plugins.md](./plugins.md) 配套：那份讲扩展的整体设计，这份讲权限怎么做成可扩展的。先后顺序统一写在 [plugins.md](./plugins.md) §12，评审记录在它的 §14。

## 1. 要解决什么

现在的权限是写死的，企业想按自己的方式管就改不了。两处最明显：

1. **管理员只能有一种结构**：有一个超级管理员，什么都能做。有的企业希望没有这样的人，几个管理员各管一块、互不越界。
2. **文档和数据上没有自己的字段**：想给文档标一个「等级」「项目」「来源」，再按这个字段决定谁能看，现在做不到。

现状：

- `rbac.Access.Super` 是一个绕过一切检查的开关，`server/internal/api` 里大约十几处直接判断它（`rbac.go` 的 `subset`、`outranks`，`hub.go`，`auth.go`，`admin.go`，`demo.go` 等）。
- 知识库只有库级的「谁能查」和「谁来维护」（[knowledge.md](./knowledge.md) 里定的「文档级权限先不做」）。
- 文档、知识库、应用、用户都没有自定义字段。

做成之后企业得到什么：

- 管理员怎么分工由企业自己定，不用迁就产品；
- 一个知识库里可以放不同范围的文档，不用为了权限把库拆成很多个；
- 人员属性从人事系统同步过来，人一调岗，能看的范围跟着变，不用手工维护名单；
- 配错了能在生效前看出来（[agent-dev.md](./agent-dev.md) 的影响范围和访问测试）。

## 2. 思路

**把写死的东西变成配置，配置表达不了的再交给扩展；判断和拦截始终在核心里做，扩展只提供数据和建议。**

权限检查散落在每个出口上（检索、读取、页面、工具、应用），如果拦截放在扩展里，扩展一出问题，就会放出不该放的东西。所以核心负责「在每个出口上按规则检查」，扩展负责「告诉核心这个人有什么属性」「这份文档的字段该填什么」「外部系统怎么判」。

三层：

| 层 | 是什么 | 谁来改 |
|---|---|---|
| 配置 | 角色、权限点、互斥约束、扩展字段、访问规则 | 管理员在界面上配 |
| 扩展 | 属性从哪来、字段怎么填、规则表达不了的判断、审计送到哪 | 写扩展（[plugins.md](./plugins.md)） |
| 核心 | 在每个出口上执行检查 | 只在 dsh-ee 里 |

## 3. 管理角色（核心，可配置）

### 3.1 不再写死超级管理员

- 管理员就是带管理类权限点的普通角色。「超级管理员」变成一个**可以关掉**的内置角色：关掉之后，`Access.Super` 永远是 `false`，所有地方只按具体权限点判断。
- 十几处直接判断 `Super` 的地方要逐个改成判断具体权限点。这是改动里最需要小心的部分，要配一组测试：关掉超级管理员后，用几种管理角色逐个调全部管理接口，核对允许和拒绝的结果。
- 权限点目录 `rbac.Catalog` 要拆得更细一些，才能把管理职责分开。比如 `users.create`（建账号）和 `roles.assign`（给人授权）分开；`audit.view` 单独一个；新增 `fields.manage`（管理字段和规则）。

### 3.2 可选的约束

这些都是开关，默认关闭，需要的企业自己打开：

| 约束 | 作用 |
|---|---|
| **互斥角色** | 指定几组角色不能由同一个人同时持有，分配时检查 |
| **不能给自己授权** | 管理员不能改自己的角色和属性 |
| **双人批准** | 指定某些操作（比如授予管理角色、修改访问规则）要另一位管理员批准才生效。流程照现有的权限申请（`server/internal/api/access.go`：提交、待批、批准后执行、全程记审计），批准人不能是发起人 |

`subset` 和 `outranks`（不能授出自己没有的权限、不能改动比自己权限大的人）保留不变。

### 3.3 预设

为了不让每家企业从零配起，内置几个预设，选了之后可以再改：

| 预设 | 内容 |
|---|---|
| 标准（默认，现状） | 一个超级管理员 |
| 分权管理 | 建系统管理员（账号、系统设置、模型、连接、扩展）、权限管理员（授权、字段和规则）、审计员（只看审计）三个角色并设为互斥；给相关管理员分好角色后，再由超级管理员关掉超级管理员（关之前会检查每个管理权限点都有人持有） |

更多的预设可以由扩展附带（[plugins.md](./plugins.md) §6.5 的「扩展附带应用」同理），也可以由管理员导出、导入。

### 3.4 切换和兜底

- 关掉超级管理员之前，系统检查：每个管理类权限点至少有一个人持有，否则不允许关，避免把自己锁在外面。
- 应急：命令行 `dsh-ee admin recover`，必须在服务器上执行，生成一个一次性的恢复账号，有效期 1 小时，审计里留下记录。审计写入失败时账号仍会创建：命令会照常打印凭据、打印严重警告并以非零退出码返回，需要人工记录该账号与到期时间并排查 `audit_logs` 表。

## 4. 扩展字段（核心，可配置）

### 4.1 字段定义

管理员在「字段与访问规则」里给几类对象加字段：

| 对象 | 例子 |
|---|---|
| 文档 | 等级、项目、来源、有效期 |
| 知识库 | 默认等级、所属项目 |
| 用户 | 等级、参与的项目、岗位 |

当前支持的对象只有文档、知识库、用户（`server/internal/access/access.go` 的 `Objects`）；应用和连接工具的字段还没实现。

字段类型：

| 类型 | 说明 | 例子 |
|---|---|---|
| `text`、`number`、`date` | 普通值 | 有效期 |
| `select` | 单选 | 来源 |
| `tags` | 多选 | 项目 |
| `level` | 有顺序的等级，定义时从低到高列出 | 普通 < 重要 < 核心 |

字段有一个开关「用于访问控制」。打开后，只有有 `fields.manage` 权限的人能改这个字段的值，修改记审计。没打开的字段只用来展示和筛选。

改字段定义时的限制，免得规则悄悄失效：

- 被访问规则用到的字段不能删，要先停掉规则；
- `level` 字段可以加新的等级、改名字，调整已有等级的顺序时要先看影响范围（[agent-dev.md](./agent-dev.md) §6.2 的 `plan`）再确认；
- 字段类型定了之后不能改，要换类型就新建一个字段。

### 4.2 字段取值

- **文档**：上传时默认取知识库上设的默认值、上传者可以改（设计，未实现：知识库字段目前只是知识库自己的属性，不会自动填到文档上；有维护权限的人在文档详情里改字段值已实现）。同步进来的文档由知识源扩展给出字段值（§6.3，已实现：只认清单声明过的字段，人手工改过的不覆盖）。
- **用户**：管理员设置，或由 LDAP / 飞书目录同步按管理员配置的映射写入（§6.1，已实现）。手工改过的值不会被下次同步覆盖，除非管理员选择「以同步为准」。
- 字段会显示在列表、详情页、检索结果上，也能用来筛选。

## 5. 按字段控制访问（核心，可配置）

### 5.1 规则

规则是在现有的库级「谁能查」之上的**附加条件**，只会收紧，不会放宽。内置三种比较方式（对字段类型有要求：等级比较要两边都是 `level` 字段且等级列表相同；有交集 / 包含要一边是 `select` 或 `tags` 字段，包含的用户侧不能是多选）：

| 比较方式 | 例子 |
|---|---|
| 等级比较 | `用户.等级 ≥ 文档.等级` |
| 有交集 | `文档.项目 ∩ 用户.项目 ≠ 空` |
| 包含 | `用户.部门 ∈ 文档.可见部门` |

- 管理员在「字段与访问规则」里组合规则，可以对全部知识库生效，也可以只对某几个知识库生效；规则作用在知识库文档上。
- 字段没填时怎么算，每条规则自己设：「当作最低」或「不限制」。默认「当作最低」，免得漏填就等于公开。
- 内置规则表达不了的，交给权限策略扩展（§6.2）。

### 5.2 要检查的地方

| 出口 | 怎么查 |
|---|---|
| `kb__search`、网页检索、知识问答 | 在算分和截取片段之前就把看不到的文档过滤掉，结果数量按过滤后的算 |
| `kb__read`、文档页、下载 | 看不到就当不存在 |
| 检索记录 | 命中的文档标题按查看者自己的权限过滤（设计，未实现：当前检索记录只存检索词和命中数，不存标题） |
| 联邦检索 | 外部知识源用员工自己的凭据查，源系统先判一遍（已实现）；返回的结果带了字段的，dsh-ee 再按规则过滤一遍（设计，未实现） |
| 连接工具、应用 | 设了字段的，按规则决定员工能不能看到、能不能用（设计，未实现：字段规则目前只作用在知识库文档上） |

检索索引里要存每个文档的字段值，过滤直接在索引查询里做，不能先查出来再一条条判断。改动不大：索引在内存里，`server/internal/kb/index.go` 的 `scope.has` 已经在按目录和指定文档过滤，字段条件加在同一个位置，标题命中和正则检索走的也是这个 `scope`。用户的字段值随登录信息一起取，改了之后下一次请求就生效。

## 6. 需要的扩展

### 6.0 字段本身也能由扩展带进来

管理员可以在界面上手工建字段（§4.1），扩展（比如用 Go SDK 写的服务扩展）也可以带字段进来，两种并存。

> 实现状态：清单 `fields` 声明的字段和安装时建字段已经实现；下面说的「建议的访问规则」「选项由扩展动态给出」还是**设计，未实现**——清单里只能写静态 `options`，规则要管理员自己建。

- 扩展在清单里写 `fields`，声明它要加的字段：对象、类型、等级顺序或选项、是否用于访问控制，也可以带建议的访问规则。比如项目管理系统的扩展带一个「项目」字段，加上一条「文档的项目和用户的项目有交集」规则。
- 安装时管理员确认后，dsh-ee 建好这些字段。字段键带上扩展的前缀（比如 `acme/pm.project`，显示名是「项目」），不会和手工建的、别的扩展建的字段冲突。建议的规则默认不启用，要管理员打开。
- 选项可以是动态的：`select`、`tags` 字段的可选值由扩展的 `options` 接口（[plugins.md](./plugins.md) §6.1）实时给出，比如项目列表直接来自项目系统，不用在 dsh-ee 里再维护一份。
- 卸载扩展时，字段和已有的值保留，变成手工字段，由管理员决定删不删。这样卸载扩展不会让访问规则突然失效（当前没有单独的卸载入口；删除连接不会级联删字段）。

扩展能决定**有哪些字段、值从哪来、选项是什么、复杂情况怎么判**；**字段值怎么存、怎么进索引、在每个出口上怎么拦**，始终由核心负责。原因有三个：

1. 检索要在索引里、算分之前就过滤，每次查询再去问外部服务，又慢，服务一挂就什么都查不出来。
2. 字段值要跟文档一起存、一起进索引、一起导出，放在扩展里就会有两份数据对不上的问题。
3. 拦截如果放在扩展里，扩展一出问题就会放出不该放的内容。

### 6.1 组织同步：带上属性

> 实现状态：LDAP / 飞书目录的属性映射已经实现（管理员在「字段与访问规则 → 同步」里把 LDAP 属性 / 飞书字段映射到用户字段）；下面说的通过扩展 `org/changes` 带字段是**设计，未实现**。

[plugins.md](./plugins.md) §6.4 已有组织同步扩展点（`org/changes`），这里补上字段：

- 返回的用户增量里可以带扩展字段：`{ id, name, dept, fields: { 等级: "重要", 项目: ["A", "B"] } }`。
- 扩展的清单里声明它会写哪些字段，安装时由管理员确认；没声明的字段写进来会被丢弃。
- 内置实现：LDAP / 飞书组织同步，把 LDAP 属性或飞书的自定义字段映射过来。

### 6.2 权限策略：规则表达不了的判断

> 有人要才做。内置的三种规则先用起来，确实表达不了再开这个口子。

[plugins.md](./plugins.md) §6.4 已有权限策略扩展点，这里补两点：

- **批量接口**：检索时一次要判断几十上百份文档，一份一份问太慢。接口是 `authorize/batch`，参数 `{ user, action, resources: [...] }`，返回每一项的 `allow` / `deny`。dsh-ee 按「用户 + 对象 + 对象版本」缓存结果，缓存时间由扩展给出，最长 5 分钟。
- **执行顺序**：先查库级权限，再查 §5.1 的内置规则，最后才问扩展；前面已经拒绝的不再问。
- 底线：只能在前面的基础上再收紧；超时或出错一律拒绝。检索时策略扩展不可用，就只返回不需要问扩展的结果，并注明有部分结果没显示。

### 6.3 字段填充（新扩展点）

> 有人要才做。知识源带字段（本节最后一条）跟着知识源一起做。

- 接口 `fields/suggest`，参数 `{ object, title, content, current }`，返回建议的字段值和理由。
- 上传、同步时调用，用来自动打标签、定等级、识别项目。**只给建议**：管理员可以设成「直接采用」或「待人确认」；对用于访问控制的字段，建议的值比当前更宽松时永远要人确认。
- 扩展连不上不影响上传，按默认值处理。
- 内置实现：关键词和正则规则，管理员在界面上配。
- 知识源扩展也可以直接在 `kb/document`、`kb/changes` 的返回里带 `fields`，比如把 Confluence 标签映射成「项目」，映射关系在挂载知识源时配置。

### 6.4 审计投递（新扩展点）

> 有人要才做。roadmap「贯穿各版」里的审计外发（syslog / Webhook）就是它的内置实现。

- 接口 `audit/deliver`，dsh-ee 按顺序批量推送审计记录，扩展返回已接收的位置；失败会重试，不会丢，也不会跳过。
- 用途：送进企业已有的日志平台或审计系统。
- 内置实现：syslog 和写入文件。

## 7. 先后顺序

统一写在 [plugins.md](./plugins.md) §12，这里只说本文的两部分：

| 批次 | 内容 |
|---|---|
| 第 3 批 | 扩展字段（文档、知识库、用户）、内置三种规则、§5.2 各出口的过滤、索引带字段；组织同步带字段；扩展带字段（§6.0）；`explain`（[agent-dev.md](./agent-dev.md) §5.2） |
| 第 4 批 | 可关闭的超级管理员和去掉 `Super` 的代码改造、互斥角色、双人批准、预设；配置导出和 `plan` / `test` / `apply` |

先做字段和规则，因为它是知识库权限的自然延伸，用处最广，而且不依赖扩展（管理员手工建字段、手工填值就能用）；动管理员结构要改授权代码的每一个地方，风险大、测试多，放在后面。`explain` 跟第 3 批一起做：规则一多，没有它管理员没法排查「为什么这个人看不到」。

## 8. 待定

1. **字段和规则先覆盖哪些对象？** 建议第 3 批只做文档、知识库、用户，应用和工具之后再加。
2. **要不要支持「按人单独授权」？** 比如某份文档额外给某个人看。这会让规则复杂不少，建议先不做，只用字段和规则。
